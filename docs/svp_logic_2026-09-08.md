# SVP-style QA logic — local implementation and evaluation

Historical v1/v2 experiment. The later [small hybrid](svp_hybrid_2026-09-08.md)
updates the local candidate; the results and closed budget below are preserved.

## Scope and deployment boundary

The new local `svp` profile implements compositional scene retrieval, not a
complete port of StructuredVP. The public Space was not deployed, reconfigured,
restarted, or given a larger allowance. The default remains `clean`; the new
profile is opt-in. PostgreSQL/server code and the previous v2 tool contract are
unchanged.

Candidate evaluated here: `svp-roles-v2`, using the existing pinned
`gpt-4.1-mini-2025-04-14`, with no reasoning step or automatic model fallback.

Outcome: the local system is more expressive and its global retrieval is better
structured, but these tests do **not** establish better overall answer grounding.
Keep it experimental. In particular, both SVP variants still omit the sofa
question's strongest outcome window from final inspection.

## What was taken from actual SVP examples

The main Gemini NExTQA examples use a planner followed by a program generator.
Their output variables carry actual retrieved subsets. For example, the
watch/running example retrieves a person, finds a watch-check **inside that
subset**, moves forward in time, finds running **inside that temporal result**,
and retrieves context around that event. The EgoSchema overall-purpose example
collects broad hierarchical activity, rather than prescribing three temporal
thirds.

Reference sources in the local StructuredVP checkout:

- `structured_vp/agent/prompt/gemini/nextqa/code.prompt`, watch/running example.
- `structured_vp/agent/prompt/gemini/egoschema/code.prompt`, overall-purpose and
  cloth-preparation examples.
- `structured_vp/execution/retrieval.py`, scoped segment search and QA sampling.
- `structured_vp/agent/controller.py`, default structural/execution controller.

We preserve typed execution and selective-only visual evidence. SVP's generated
Python execution, full-video frame input, and exhausted-iteration full-video
fallback are deliberately not copied. Its opt-in iterative symbolic controller
is separate from its standard planner/program workflow; this implementation
does not claim to reproduce that agent loop.

## Implemented changes

| Capability | Preserved baseline | New local SVP profile |
| --- | --- | --- |
| Program representation | All `locate` calls, then all `relate` calls | Up to eight ordered, typed operations |
| Search scope | Full cached video or fixed third | `source="video"` or a previous result |
| Composition | Temporal traversal from earlier results | Entity → event → temporal context → scoped event → further context |
| Final inspection | Direct queries and relations must be included | Only chosen terminal outputs; ancestors may be navigation only |
| Global objective | Three mandatory temporal-third searches | Diverse cached overview plus question-specific corroboration |
| Execution feedback | No retry after coverage failure | One compiler revision using actual failed candidates and gaps |
| Inspection attention | Every scene gets every evidence need | Each scene receives the needs attached to its selected output |

`locate`, `relate`, and `overview` return real ranked results. Their trace records
input source IDs, eligible scene IDs, scores, hits and ancestry. An empty input
stays empty. A broader search must be an explicit new operation, not a hidden
fallback. `relate` uses its first ranked source as the anchor; a temporal neighbor
is not automatically a verified semantic event. Window overlap is flagged and
never presented as proof of event order.

Overview starts with a semantic medoid, then selects representatives using
semantic novelty and temporal spread. Its diversity score is labelled separately
from cosine similarity. Whole-video requests must retain a direct-video overview
as an inspection source. The selector checks representative coverage under the
same interval/seconds limits; it does not invent complete coverage when the
budget cannot accommodate it. This is a bounded adaptation of SVP's broad
context, not an action index or proof that every event was observed.

The controller validates references, need/dependency linkage, dead outputs and
budgets before execution. Retrieval is deterministic for fixed embeddings and
programs. Structural JSON repairs and the one execution-feedback retry are
separate, explicitly traced, and share the same request allowance.

The visual limits remain three windows, 60 seconds of selected spans, six final
frames per window, and at most one additional focused inspection. Search distance
does not consume visual seconds; choosing a short pixel budget does not require
an equally short temporal search horizon.

## Prompt tuning, not a smaller reasoning task

The planner remains blind to the video. The tool compiler receives the plan and
fallible cached timeline, and generates the complete ordered program. Seven
fictional paired demonstrations cover scoped identity/event search, subsequent
action, transport purpose, interleaved events, preceding cause, object-function
context and global objectives. A small relevant subset is included per request.
They are teaching examples, not recorded tool observations or benchmark answers.

V2 responds to two observed V1 failures:

- For purpose questions, treat already-stated transport as one anchor and search
  for its unknown outcome, rather than spending all evidence on pickup/arrival.
- For global objectives, preserve diverse overview evidence instead of taking
  `during` one top-ranked event and calling that global progression.

The compiler can use a concrete cached action as a search hypothesis, but only
fresh images can support the answer. Additional temporal hops should re-localize
the intermediate semantic event, not simply rename a neighboring window.
No generic ban removes valid dependency chains, short immediate horizons, or
complex interleaved programs.

OpenAI Docs guidance informed the explicit tool contracts, concise role rules,
paired examples and empirical iteration. We retain schema-constrained program
generation through the existing transport; this is not a claim of implementing
API-native function calling. [Official GPT-4.1 prompting guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-4.1).

## Evaluation protocol

Clean, SVP V1 and SVP V2 use the same video bytes, historical captions, normalized
384-dimensional vectors and pinned model for each case. Captioning is not rerun.
Each candidate has an isolated cache with the rebinding recorded explicitly.
Selected pixels may change: this evaluates retrieval plus targeted inspection,
not prompt wording on identical frames. The downstream choice, answer and review
prompts remain the clean baseline.

Cases: NExTQA gift/sofa purpose (multiple choice) and EgoSchema kitchen objective
(open-ended). These are known regression cases, not held-out benchmark estimates.
Each profile/case runs once; paired runs overlap in wall time, so reported latency
is descriptive, not a controlled load benchmark. Grounding is checked against
actual selected images independently of the model's review vote.

All outputs, failures, manifests and request/image/schema hashes are retained in
`artifacts/svp_logic_2026-09-08`. The original four runs consumed 36 HTTP attempts.
The [explicit protocol amendment](svp_evaluation_protocol_2026-09-08.md) permits
one V2 run per case within the **same 60-attempt total**, with no reset or new
request allowance. Each additional run is capped at 12 attempts.

### Sofa: better program, still weaker final evidence than clean

V2 correctly combines transport into one anchor and requests an unknown outcome.
Its real program is:

```text
locate("boy picks up present and moves to sofa", source="video")
    → [0, 3, 2, 1]
relate(after, source=present_pickup, horizon_seconds=30)
    → [1, 0, 2]
locate("boy actions with present at sofa", source=sofa_interaction_search)
    → [0, 1, 2]
inspect(present_pickup, sofa_interaction)
    → [0, 1, 2]
```

The second locate really stays within its source. The failure is now visible:
the anchor search prefers scene 0; the temporal horizon then excludes scene 3
from outcome search. Scene 3 was found initially, but final selection prefers
scenes appearing in both terminal result lists. It is not a fabricated retrieval
or an entirely missing index entry.

Scene 2 already contains material separation/contents near 50.26–53.76s, so the
answer is not without visual support. Clean also retains scene 3, with clearer
paper separation at 57.77/64.77s and fabric-like contents at 68.27/71.77s. V2's
better-sampled pickup is useful setup but does not replace that stronger outcome.
The selected duration does not decrease.

Grounding errors remain: V2 narrates pickup at 18.25s when the object is already
held; it describes tree-side pickup as sofa-side; its alternative comparisons
treat absence as contradiction and alter the lady option into approaching to
share. Clean falsely claims nobody is visible on or near the sofa despite the
adult helping in its own frames. Both reviews miss these errors.

### Kitchen: useful global overview, remaining identity errors

V1 used `during` one best-ranked cleaning scene, then a scoped overview. V2
actually executes a direct-video overview:
`[2, 8, 4, 0, 6, 1]`, retaining three representatives `[2, 4, 8]` under 60 seconds.
This covers the baking dish, plates/cup, and later glass handling, without the
old mandatory thirds or V1's two adjacent early windows.

The planner still adds a generic action-outcome dependency, so the compiler
also produces an `after` relation from the overview's first representative.
That does not establish outcomes for every action in the video. It is a remaining
planning limitation, not proof of full-video causal understanding.

V2 avoids the baseline's unsupported assertion that visible water flow is absent
and its blue-pad/brush misidentification on the red board. It also explicitly
limits claims about cleaning effectiveness. However, the inspector misstates
some exact plate actions, calls the held glass at 175.85s a pan, and claims a
different glass without established identity. The answer inherits pan-cleaning
in scene 8, where static pans on the rack are not evidence of that action. The
model accepts these errors. Broader evidence is useful, but grounding is not solved.

### Reproducibility and checks

The full offline suite passes: **969 tests**; Ruff is clean. Tests include scoped
containment, relation→locate composition, empty propagation, graph/dependency
failures, strict hosted schemas, exact budgets, global representative coverage,
two-attempt execution stopping, profile isolation and preserved v2 behavior.

Every run retains its prompt snapshots and real wire hashes. V2 core/runtime
sources were frozen before both calls and are saved in `source-snapshots.json`.
V1 core/prompt archives match all four manifests. Exact manifest-hashed V1 runtime
snapshots are preserved separately for the sofa and kitchen pairs: a concurrent
negative-ID guard change distinguishes those pairs; a later whitespace-only-query
guard distinguishes the top-level V1 archive. Neither invalid input occurs here.
Disk hashes are not independently captured in-memory module bytes; no stronger
provenance claim is made for those concurrent V1 runs.

Actual reports: [V2 sofa](../artifacts/svp_logic_2026-09-08/svp__svp-roles-v2__sofa_mc/report.json)
and [V2 kitchen](../artifacts/svp_logic_2026-09-08/svp__svp-roles-v2__kitchen_open/report.json).
The corresponding directories retain raw traces, selected images and visual
contact sheets. The next quality bottlenecks are semantic anchor resolution,
outcome-aware final selection and action/object identity—not adding more generic
instructions to the final answer prompt.

## Remaining differences and limits

This is scene-level compositional retrieval with fresh visual inspection. A
separate timestamped atomic-action memory, object entities/crops, spatial
relations, and observation-driven tool selection are **not implemented**. Cached
scene captions are still fallible and windows are uniform, not learned event
boundaries. An empty-result retry is not perceptual replanning after inspection.

The answerer still uses a fixed multiple-choice candidate, and the visual
reviewer remains fallible. Better tool dataflow does not itself fix object
misidentification, invented transitions, or treating unseen alternatives as
contradicted. No promotion or accuracy claim should rely only on successful
execution, the selected choice, or the review badge.

## Local entry points

- Prompts: `src/videomasys/zerogpu/svp_prompts.py`.
- Typed tools, validation and retrieval: `src/videomasys/zerogpu/svp_retrieval.py`.
- Integration/controller: `src/videomasys/zerogpu/core.py`.
- Explicit local construction: `RemotePipeline(..., prompt_profile="svp")`.
- Evaluation: `scripts/evaluate_svp_logic.py`; default is a no-key dry-run.
- Actual-frame contact sheets: `scripts/review_svp_frames.py`.

Do not change the public Space's `VLM_PROMPT_PROFILE` or run a deployment script
as part of this experiment.
